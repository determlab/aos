# AOS Processor SDK — spec v0.2

Source: chat session 2026-08-29. Owner context: SHAL and Bricks are both determlab
repos, zero external users → full freedom to change APIs.

---

## 1. What this is (30 seconds)

We dropped the "general Agent OS" framing. Instead:

> **Build purpose-built agent processors.** One processor = one capability set + one
> trigger + one policy, defined in a manifest. A tiny kernel runs them. The OS emerges
> from repetition — like Unix did.

MVP processor: **daily-calendar-summary** — reads one calendar, produces a morning
summary, needs only one revocable read-grant.

---

## 2. Decisions locked

> **The locked decisions live in [`docs/DECISIONS.md`](../docs/DECISIONS.md), and only
> there.** D1–D10 were settled in the same 2026-08-29 session as this document; the
> ledger carries them in claim form, with their provenance and whether each is true in
> the code today. Issues cite them by number (`implements D8`). Never renumber.
>
> They are **not** restated here. A decision number is stable for the life of the
> product while this file is a versioned snapshot, and two copies of the same claim
> means one of them drifts — as §4.1 already has (D11 supersedes its `risk:` field).
> The ledger wins on every point of conflict.

What the ledger cannot hold, because a one-line claim has no room for it:

- **The nondeterminism the boundary in D4 is about is the LLM.** The kernel is a
  deterministic wrapper; a model call, if a processor ever makes one, is the
  executor's business and stays inside it. That is why "zero tokens per run" (D5) is
  a property of the MVP, not of the kernel.
- **D7 in the concrete.** Capability id `cal_personal.read_events` is the SHAL tool
  `cal_personal__read_events` — the same identifier with the separator swapped, in
  both directions, with nothing to look up. This is what closed the "capability
  schema" open question from v0.1: there is no schema, there is a naming convention.
- **D8's failure mode is a status, not an exception.** A missing brick makes
  `run_blueprint` fail *validation*, so the run ends `status: denied` before a single
  step executes. Denial by construction — see §5, rules 1–3.
- **D9 costs no new SHAL code.** SHAL already halts a gated op pre-I/O and asks
  whatever `Approver` is installed. Registering the kernel as that approver is what
  buys the `APPROVAL_REQUIRED` policy state, audited, for free.

## 3. The stack

```
Processor manifest (yaml)
        |
   AOS KERNEL        grants check (fail fast) · run record (always)
        |
     BRICKS          blueprint = deterministic DAG of typed steps
        |            capability bricks injected per-run from grants
   GATEWAY           per-call grant check + audit entry
        |
      SHAL           topology · drivers · retry · write-approval gate · txn log
        |
   RESOURCE          Google Calendar (http node) today · robots/PLCs later
```

## 4. Minimal data model — v0.2

Five artifacts on disk. Four written by hand, one by the runtime.

### 4.1 Capability (contract) — `capabilities/`
```yaml
capability: cal_personal.read_events
input:  { date_from: date, date_to: date }
output: { events: list }        # {title, start, end, attendees}
risk: read                      # read | write | dangerous
```

### 4.2 Topology (resources + drivers) — `lab.yaml` (SHAL)
```yaml
shal_version: 1
root:
  services:
    driver: shal,http
    address: https://www.googleapis.com
    children:
      cal: { id: cal_personal, driver: determlab,google-calendar,
             address: calendars/primary }
# credentials via ${ENV}, never logged
```

### 4.3 Grant (authorization) — `grants/`
```yaml
grant: grant-001
principal: user:me
processor: daily-calendar-summary
capability: cal_personal.read_events
mode: read_only
expires: 2026-12-31
revoked: false
```
Runtime rule: no matching, unexpired, unrevoked grant → run stops. No exceptions.

### 4.4 Processor manifest — `processors/`
```yaml
processor: daily-calendar-summary
version: 0.2
requires: [cal_personal.read_events]
blueprint: blueprints/daily-summary.yaml
trigger: { cron: "0 7 * * *" }
engine: bricks
policy: { grants_required: true }
output: { deliver: push, target: "user:me" }
```

### 4.5 Run record (audit) — `runs/`, written by runtime in `finally`
```yaml
run: run-abc123
processor: daily-calendar-summary
started: 2026-08-29T07:00:01Z
ended:   2026-08-29T07:00:14Z
status: success                 # success | failed | denied
calls:
  - { capability: cal_personal.read_events, grant: grant-001,
      shal_txn: "…", result: ok }
output_ref: outputs/run-abc123.txt
error: null
```
One trace end-to-end: SHAL `txn` id + Bricks step attribution both land here.

### Deliberately missing (add only when a real processor forces it)
Multi-step workflow state · events between processors · sandbox spec · multi-tenant
identity.

## 5. Engine — target run loop (v0.2 sketch)

```python
# aos/engine.py — kernel loop wired to Bricks + SHAL
import shal
from bricks import build_default_registry, run_blueprint

def run(processor_id):
    record = new_record(processor_id)                    # status: running
    try:
        m = load_manifest(processor_id)
        for cap in m["requires"]:                        # fail fast
            require_grant(processor_id, cap)

        hal = shal.load("lab.yaml")                      # resources + drivers
        reg = build_default_registry()                   # 101 pure stdlib bricks
        for cap in m["requires"]:                        # grants -> bricks
            node, op = cap.split(".")
            reg.register(cap.replace(".", "_"),
                make_capability_brick(hal, node, op, record))  # logs + calls hal.call_tool

        result = run_blueprint(m["blueprint"], inputs=today(), registry=reg)
        deliver(m["output"], result)                     # e.g. push
        record.finish("success", result)
    except PermissionError as e:
        record.finish("denied", error=str(e))
    except Exception as e:
        record.finish("failed", error=str(e))
    finally:
        write_run_record(record)                         # ALWAYS
```

Three rules the code must keep:
1. The blueprint can only see bricks that exist in `reg` → policy = validation.
2. `make_capability_brick` is the single door: grant + audit + `hal.call_tool`.
3. `write_run_record` runs in `finally` — success, failure, or denial.

> **Correction applied during review:** `Registry.register` takes **three** arguments —
> `register(name, callable_, meta: BrickMeta)` (`bricks/core/registry.py:22`). The
> sketch above passes two. Each capability brick needs a `BrickMeta`.

## 6. Because both repos are mine — leverage moves

1. **`bricks-shal` pack (inside bricks repo).** Auto-generate one brick per SHAL
   `tool_schemas()` entry. Kills `make_capability_brick` boilerplate for every future
   processor.
2. **`AOSApprover` adapter (inside shal repo).** Documented hook so SHAL
   write-approvals become AOS approval-gate items.
3. **Unify trace ids now.** One run id flows AOS → Bricks steps → SHAL txns, before
   any user depends on current formats.
4. **New repo `determlab/aos`** for the kernel + spec. Keep it small on purpose; the
   repos stay: aos (who may do what) · shal (how it reaches the thing) · bricks (in
   what order).

## 8. MVP build plan — daily-calendar-summary

1. Create repo `determlab/aos`; commit this doc as `spec/v0.2.md`.
2. `pip install pyshal`; run the SHAL sim quickstart (zero hardware) → green.
3. Write `determlab,google-calendar` SHAL driver: one class, one `@op` read
   (`side_effect="none"`), copy the Tmp102 shape.
4. Add the calendar node to `lab.yaml`; `shal probe lab.yaml` shows events.
5. Clone bricks, `pip install -e .`, **pin the commit** (alpha, no PyPI yet); run one
   example blueprint.
6. Write `blueprints/daily-summary.yaml`: read_events → filter today → sort → template
   summary. Zero LLM.
7. Write the engine loop from section 5 (~150 lines).
8. Denied test: delete the grant file, run → expect `status: denied` + a run record
   still written.
9. Cron `0 7 * * *`; live with it for 5 mornings.
10. Processor #2 with a different capability. Whatever breaks in the manifest = the
    next spec change.

**Definition of done for the MVP:** one YAML manifest, one grant, one blueprint, zero
tokens per run, and an audit record for every run including denials.
